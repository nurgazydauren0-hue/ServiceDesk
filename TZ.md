# Техническое задание: ServiceDesk

## Назначение

Система внутренних IT-заявок компании. Сотрудник создаёт обращение, администратор назначает исполнителя, исполнитель решает проблему и ведёт переписку. Данные сохраняются в PostgreSQL; обновление страницы и перезапуск приложения не удаляют записи.

## Стек

Next.js App Router, React, Tailwind CSS, PostgreSQL, Prisma ORM, Auth.js, Zod, Lucide React и Recharts. Совместимые версии зафиксированы в lockfile. Секреты хранятся в переменных окружения.

## Пользовательские разделы

- Dashboard: реальные счётчики статусов, последние заявки и диаграмма.
- Все / мои заявки: таблица, поиск, фильтры по статусу и приоритету, сортировка.
- Новая заявка: название, описание, категория и приоритет с серверной проверкой.
- Детали: автор, исполнитель, даты, статус, описание и комментарии.
- Команда: пользователи, роли и количество назначенных задач; управление ролями администратором.
- Отчёты: распределение по статусам и приоритетам, количество обращений по датам.
- Профиль / настройки: данные текущего пользователя и изменение имени.
- Регистрация и вход: безопасная сессия и защищённые разделы.

## База данных

| Сущность | Основные поля |
| --- | --- |
| User | id, name, email, passwordHash, role, createdAt |
| Ticket | id, title, description, status, priority, categoryId, createdById, assignedToId, createdAt, updatedAt |
| Category | id, name |
| Comment | id, ticketId, authorId, content, createdAt |

Для связей используются внешние ключи. Автор заявки, автор комментария и категория должны существовать. Исполнитель необязателен. Структура воспроизводится миграциями Prisma. Основные категории и первый администратор создаются bootstrap; примеры для защиты создаются отдельным явным seed.

## Роли и ограничения

Сотрудник создаёт и видит свои заявки, пишет комментарии; редактирует и удаляет свою новую неназначенную заявку. Исполнитель дополнительно видит назначенные ему обращения и меняет их статус. Администратор видит все данные, назначает исполнителей, управляет ролями и заявками. Самостоятельная регистрация всегда создаёт сотрудника.

Сервер проверяет актуальную роль, доступ к конкретной заявке и разрешённые поля операции. Проверка интерфейса не заменяет серверную. Dashboard ограничивается той же областью доступа, что и список заявок. Полные отчёты доступны администратору.

## Интерфейс

Светлая корпоративная палитра: белый, графитовый, тёмно-синий и бирюзовый. Сворачиваемая боковая панель имеет одну кнопку управления. Верхняя панель показывает текущий раздел и один аватар с меню профиля. Нужны адаптивность, подписи полей, клавиатурный фокус, понятные ошибки, загрузка и пустые состояния.

Главный текст: «Управляй заявками. Решай задачи быстрее.» Подзаголовок: «Все обращения сотрудников, статусы выполнения и работа команды — в одной системе.»

## Критерии приёмки

1. Новый пользователь регистрируется, входит и создаёт заявку.
2. Запись и комментарии сохраняются в PostgreSQL после перезапуска сервера.
3. Другой сотрудник не получает заявку прямым запросом API или страницы.
4. Администратор назначает исполнителя; только соответствующий исполнитель и администратор управляют статусом назначенной заявки.
5. Некорректные поля и попытки самовольного повышения роли отклоняются сервером.
6. Поиск, фильтры, сортировка и переходы работают на реальных данных.
7. Статистика изменяется вслед за данными в разрешённой области видимости.
8. Закрытые страницы и API требуют входа; выход прекращает доступ.
9. README позволяет повторить установку, миграции, bootstrap, seed, сборку и тестирование.
10. Отдельная PostgreSQL-база используется для интеграционных тестов; рабочие данные не очищаются тестами.

## Разделение работы

Frontend/UI: страницы, компоненты, формы, таблицы, диаграммы, адаптивность и обработка ответов. Backend/Database: Prisma, PostgreSQL, миграции, авторизация, права, валидация, API и тесты. Оба участника согласуют API, проверяют полный сценарий и могут объяснить путь данных.
