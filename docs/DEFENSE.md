# ServiceDesk: сценарий защиты

«ServiceDesk — система внутренних IT-заявок компании. Сотрудник описывает проблему, администратор назначает исполнителя, исполнитель решает её и отвечает в комментариях. Next.js обслуживает React-интерфейс и API, Auth.js управляет сессией, Prisma работает с PostgreSQL. Сервер проверяет роль и права на каждую операцию. Работа разделена между Frontend/UI и Backend/Database».

Говорите своими словами и открывайте конкретный экран или файл вместо пересказа списка технологий.

## Подготовка

Запустите PostgreSQL и приложение по README. Для показа используйте отдельную демонстрационную базу и явный seed. Запомните заданный вами `SEED_DEMO_PASSWORD`. Откройте сотрудника, исполнителя и администратора в разных профилях браузера, чтобы не переключать одну сессию во время показа. Не показывайте `.env` и реальные пароли на экране.

## Показ на 7–10 минут

1. **Назначение, 1 минута.** Frontend показывает Dashboard, адаптивную навигацию, список и профиль. Объясняет, что показатели получены из доступных пользователю заявок.
2. **Создание, 1–2 минуты.** Сотрудник создаёт заявку «Не работает Wi-Fi» с категорией и приоритетом. Frontend показывает `POST /api/tickets` в Network и объясняет JSON, загрузку и обработку ответа.
3. **Сервер и база, 2 минуты.** Backend открывает обработчик маршрута, Zod-схему и модель Prisma. Объясняет последовательность: сессия, проверка прав и полей, запись PostgreSQL, ответ `201`. В Prisma Studio можно показать созданную строку.
4. **Роли и работа команды, 2 минуты.** Администратор назначает исполнителя. Исполнитель меняет статус и пишет комментарий. Сотрудник видит обновление и отвечает.
5. **Изоляция и сохранение, 1 минута.** Другой сотрудник открывает прямой URL этой заявки и не получает данные. Обновите страницу, затем при возможности перезапустите сервер и снова покажите заявку.
6. **Отчёты и качество, 1–2 минуты.** Покажите изменение реальных счётчиков, unit- и интеграционные тесты, миграции и README. Завершите демонстрацию GitHub-репозиторием и личным вкладом каждого участника.

## Что объяснить в коде

| Вопрос | Понятное объяснение |
| --- | --- |
| Почему Next.js? | React-страницы и серверные маршруты работают в одном приложении. |
| Зачем Auth.js? | Он обрабатывает вход и сессию. Регистрация отдельно проверяет и сохраняет пользователя. |
| Где пароль? | В базе только scrypt-хеш с солью; исходный пароль не сохраняется. |
| Почему скрытой кнопки недостаточно? | Запрос можно отправить вручную, поэтому сервер повторно проверяет полномочия. |
| Как сотрудник видит только свои заявки? | Сервер ограничивает запрос к базе по идентификатору текущего пользователя. |
| Что происходит при смене роли? | Сервер получает актуальную роль из записи пользователя, а не доверяет данным формы. |
| Что даёт Prisma? | Связанные модели, запросы к PostgreSQL и воспроизводимые миграции структуры. |
| Почему данные не исчезают? | Они записаны в PostgreSQL, независимо от состояния React и процесса Next.js. |
| Откуда статистика? | Она рассчитывается по тем же реальным заявкам, к которым пользователь имеет доступ. |
| Для чего seed? | Чтобы явно создать демонстрационные записи в отдельной базе; обычный запуск его не вызывает. |
| Что проверяют тесты? | Unit — правила и данные; integration — настоящий сервер, сессии, роли и PostgreSQL. |

## Границы текущего проекта

Основной сценарий включает заявки, роли, назначения, комментарии и отчёты. Почтовые уведомления, вложения, интеграция с корпоративным каталогом, SLA и восстановление пароля не заявляются как готовые функции. Для эксплуатации в компании потребуются её правила доступа, мониторинг, резервные копии и процедура восстановления.

Перед защитой каждый участник должен найти в коде один полный путь от формы до PostgreSQL и объяснить его без чтения готового текста.
