## 1. Вступление — 30 секунд

Здравствуйте. Я Dauren, в проекте ServiceDesk я отвечал за серверную часть и базу данных.

ServiceDesk — система заявок в IT-отдел. В ней три роли: сотрудник сообщает о проблеме, ИТ-специалист её решает, администратор распределяет работу и смотрит отчёты.

Все данные хранятся в PostgreSQL 17 в облачном сервисе Neon. Поэтому мы с Аминой работаем с одной базой и видим одни и те же данные.

Браузер никогда не подключается к базе напрямую. Запрос идёт так: страница → сервер Next.js → Prisma ORM → PostgreSQL. Пароль от базы хранится только на сервере, в файле `.env`, и в GitHub не попадает.

## 2. Таблицы и связи — 1,5 минуты

**▶ Вкладка 2 (Neon → Tables). Пощёлкайте по таблицам.**

Вот наша база в Neon. Основных таблиц четыре:
- `User` — пользователи всех трёх ролей;
- `Category` — категории заявок: оборудование, сеть, доступы и так далее;
- `Ticket` — заявки;
- `Comment` — переписка по заявке.

Ещё есть две служебные таблицы. `AuthRateLimit` ограничивает число попыток входа, чтобы нельзя было подобрать пароль. `_prisma_migrations` хранит историю изменений структуры.

**▶ Вкладка 4 (ER-диаграмма).**

Все связи здесь «один ко многим». Пользователь создаёт много заявок. В категории много заявок. У заявки много комментариев.

Между пользователем и заявкой две связи: автор и исполнитель. Автор обязателен. Исполнителя может не быть — тогда заявка «не назначена».

**▶ Вкладка 3 (SQL Editor). Запустить 1.4.**

Это внешние ключи прямо из PostgreSQL. В последнем столбце видно, что происходит при удалении:
- **RESTRICT** — категорию, в которой есть заявки, удалить нельзя;
- **CASCADE** — если удалить заявку, её комментарии удалятся вместе с ней;
- **SET NULL** — если удалить исполнителя, заявка останется, но станет без исполнителя.

**▶ Запустить 1.3.**

Роли, статусы и приоритеты сделаны через ENUM — фиксированный список значений. Ничего другого база не примет.

## 4. Центр поддержки из базы — 1,5 минуты

**▶ Вкладка 1 (приложение) → «Центр поддержки».**

В приложении есть центр поддержки. Администратор видит, кто из пользователей ждёт ответа, что просрочено и сколько работы у каждого ИТ-специалиста. ИТ-специалист видит свою очередь. Пользователь видит переписку по своим обращениям.

Отдельной таблицы для этого нет. Всё считается из уже существующих таблиц `Ticket` и `Comment`.

**▶ Вкладка 3. Запустить 3.5.**

Этот запрос делает то же, что сервер. Для каждой открытой заявки он берёт последнее сообщение переписки — через подзапрос `LATERAL` с сортировкой по дате. Дальше логика простая:
- последним написал пользователь или сообщений нет — значит, заявка **ждёт ответа поддержки**;
- последним написал специалист — **специалист работает**;
- статус «Ожидание» — **ждём пользователя**.

Если заявка ждёт поддержку дольше нормы для своего приоритета (срочная — 2 часа, высокая — 8, средняя — 24, низкая — 72), она **просрочена**.

Сравните с экраном: просроченные заявки совпадают. Запрос работает быстро, потому что у таблицы комментариев есть индекс по заявке и дате.

## 5. Права доступа — 1 минута

**▶ Запустить 4.1, 4.2, 4.3 по очереди.**

Таблица заявок одна, но каждая роль видит свою часть. Сервер сам добавляет к каждому запросу условие WHERE:
- сотрудник — только свои заявки;
- ИТ-специалист — назначенные ему и созданные им;
- администратор — все.

Видно, что количество строк разное. Роль берётся из базы, а не из браузера, поэтому подменить её нельзя. Чужую заявку не получить даже прямым запросом к API: база просто не вернёт эту строку.

## 6. Целостность — 1 минута

Теперь покажу, что база сама защищает себя от неправильных данных. Каждый из этих запросов специально неправильный и должен закончиться ошибкой.

**▶ Запустить 5.1** — заявка с несуществующей категорией: ошибка внешнего ключа.

**▶ Запустить 5.2** — второй пользователь с тем же email: ошибка уникальности.

**▶ Запустить 5.3** — статус «DONE», которого нет в списке: ошибка ENUM.

**▶ Запустить 5.6** — удалить категорию, в которой есть заявки: ошибка RESTRICT.

Даже если обойти приложение, база не примет неправильные данные. Проверка идёт на трёх уровнях: схемы Zod на сервере, Prisma и ограничения самой PostgreSQL.

## 8. Заключение — 20 секунд

Итого: база ServiceDesk реляционная, в третьей нормальной форме, таблицы связаны внешними ключами. Пароли хранятся только в виде хеша. Права проверяются на сервере для каждого запроса. Изменения выполняются в транзакциях, а структура меняется через миграции. Даже центр поддержки работает без лишних таблиц — он считается запросом из заявок и комментариев.

## Шпаргалка для вопросов

| Вопрос | Короткий ответ |
| --- | --- |
| Почему PostgreSQL? | Данные связанные, нужны внешние ключи, транзакции и строгие ограничения. |
| Первичный ключ? | Однозначно определяет строку, например `Ticket.id`. |
| Внешний ключ? | Ссылка на первичный ключ другой таблицы: `Ticket.categoryId` → `Category.id`. |
| Какая нормальная форма? | Третья: каждый факт хранится один раз, категория — только в `Category`. |
| Что такое транзакция? | Группа операций, которая выполняется целиком или не выполняется совсем. |
| Зачем индексы? | Чтобы не перебирать всю таблицу. Например, последний комментарий заявки находится по индексу. |
| Что такое миграция? | SQL-файл изменения структуры; применённые миграции записаны в `_prisma_migrations`. |
| Зачем Prisma? | Работа с таблицами как с объектами в коде; значения передаются параметрами, поэтому SQL-инъекция невозможна. |
| Почему у заявки id — число? | Номер видят люди (SD-0137). У пользователей cuid: его нельзя угадать перебором. |
| Где центр поддержки в базе? | Отдельной таблицы нет: состояние считается по последнему комментарию заявки (запрос 3.5). |
| Что такое LATERAL? | Подзапрос, который выполняется для каждой строки и может ссылаться на неё — здесь «последний комментарий этой заявки». |

Полные ответы на 15 вопросов — в [DATABASE.md](DATABASE.md), раздел «Вопросы, которые может задать преподаватель».
