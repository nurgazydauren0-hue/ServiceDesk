## 1. Вступление (30 секунд)

Здравствуйте. Я Dauren, в проекте ServiceDesk я отвечал за серверную часть и базу данных.

ServiceDesk — это система заявок: сотрудник сообщает о проблеме, исполнитель её решает, а администратор следит за работой и смотрит отчёты.

Все данные хранятся в базе PostgreSQL 17. База находится в облаке Neon, сервер во Франкфурте. Поэтому мы с Аминой работаем с одной и той же базой и видим одинаковые данные.

Приложение подключается к базе через Prisma ORM. Браузер к базе напрямую не подключается никогда: запрос идёт от страницы к серверу Next.js, сервер через Prisma обращается к PostgreSQL. Адрес и пароль базы лежат в файле `.env`, который не загружается на GitHub.

## 2. Структура базы (1 минута)

**▶ [Запустить 1.1 — список таблиц]**

В базе четыре основные таблицы: `User` — пользователи, `Category` — категории, `Ticket` — заявки и `Comment` — комментарии.

Есть ещё две служебные: `AuthRateLimit` ограничивает число попыток входа, чтобы нельзя было подобрать пароль, а `_prisma_migrations` хранит историю изменений структуры.

**▶ [Показать ER-диаграмму в DATABASE.md на GitHub]**

Связи все один-ко-многим. Один пользователь создаёт много заявок. Одна категория содержит много заявок. У одной заявки много комментариев. У пользователя с заявкой две связи: как автор и как исполнитель. Исполнителя может не быть, тогда заявка «Не назначена».

**▶ [Запустить 1.2 — поля таблицы Ticket]**

Вот поля заявки. У каждого поля свой тип. Например, название — не длиннее 160 символов, автор и категория обязательны, а дата решения `resolvedAt` пустая, пока заявка не решена. По ней мы считаем среднее время решения в отчётах.

**▶ [Запустить 1.3 — ENUM]**

Роли, статусы и приоритеты сделаны через ENUM, то есть через фиксированный список значений. База просто не примет статус, которого нет в этом списке.

**▶ [Запустить 1.4 — внешние ключи]**

Здесь видны внешние ключи и что происходит при удалении. Категорию, в которой есть заявки, удалить нельзя — это RESTRICT. Если удалить заявку, её комментарии удаляются вместе с ней — это CASCADE. Если удалить исполнителя, заявка остаётся, но становится без исполнителя — это SET NULL.

## 3. Данные и связи (1 минута)

**▶ [Запустить 2.2 — пользователи]**

Это пользователи. Обратите внимание на последний столбец: пароль в базе не хранится. Хранится только scrypt-хеш с солью. Из хеша пароль восстановить нельзя, можно только проверить, подходит ли введённый.

**▶ [Запустить 2.3 — JOIN заявок]**

Этот запрос собирает заявку из трёх таблиц с помощью JOIN: из `Ticket` берётся сама заявка, из `Category` — название категории, из `User` — имя автора и исполнителя. Название категории хранится только в одном месте, в заявке лежит лишь ссылка на неё. Так данные не дублируются — это третья нормальная форма.

Графики и отчёты в приложении считаются такими же запросами. Здесь количество заявок по статусам, а здесь — сколько заявок у каждого исполнителя и среднее время решения в часах. Цифры совпадают с тем, что показывает приложение.

## 5. Права доступа (1 минута)

**▶ [Запустить 4.1, 4.2, 4.3 по очереди]**

Таблица заявок одна, но каждая роль видит свою часть. Сервер сам добавляет к запросу условие WHERE по роли.

Сотрудник видит только свои заявки. Исполнитель — назначенные ему и созданные им. Администратор — все. Видите, количество строк разное.

Роль берётся из базы, а не из формы в браузере, поэтому её нельзя подменить. Чужую заявку нельзя получить даже прямым запросом к API: база просто не вернёт эту строку.

## 6. Целостность данных (1–2 минуты)

Теперь покажу, что база сама защищает себя от неправильных данных. Каждый следующий запрос специально неправильный и должен закончиться ошибкой.

**▶ [Запустить 5.1]** — заявка с несуществующей категорией. Ошибка внешнего ключа.

**▶ [Запустить 5.2]** — второй пользователь с уже занятым email. Ошибка уникальности.

**▶ [Запустить 5.3]** — статус «DONE», которого нет в списке. Ошибка ENUM.

**▶ [Запустить 5.4]** — название длиннее 160 символов. Ошибка длины.

**▶ [Запустить 5.6]** — удалить категорию, в которой есть заявки. Ошибка RESTRICT.

То есть даже если обойти приложение, база не примет неправильные данные. Проверка идёт на трёх уровнях: схемы Zod на сервере, Prisma и сами ограничения PostgreSQL.

Итого: база ServiceDesk реляционная, в третьей нормальной форме, таблицы связаны внешними ключами. Пароли хранятся только в виде хеша, права проверяются на сервере для каждого запроса, изменения выполняются в транзакциях, а структура меняется через миграции. Спасибо, готов ответить на вопросы.

## Шпаргалка для ответов на вопросы

- **Почему PostgreSQL?** Данные связанные, нужны внешние ключи и транзакции.
- **Первичный ключ** — однозначно определяет строку. **Внешний ключ** — ссылка на первичный ключ другой таблицы.
- **Нормальная форма** — третья: данные не дублируются, категория хранится один раз.
- **Транзакция** — группа операций, которая выполняется целиком или не выполняется совсем.
- **Индекс** — «оглавление» по столбцам, чтобы не перебирать всю таблицу.
- **Миграция** — SQL-файл изменения структуры; применённые миграции записаны в `_prisma_migrations`.
- **ORM / Prisma** — работа с таблицами как с объектами в коде; значения передаются параметрами, поэтому SQL-инъекция невозможна.
- **Почему id заявки — число?** Номер показывается людям (SD-0137). У пользователей — cuid, его нельзя угадать перебором.

Полные ответы на 15 вопросов — в [DATABASE.md](DATABASE.md), раздел «Вопросы, которые может задать преподаватель».
