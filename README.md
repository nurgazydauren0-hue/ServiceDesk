# ServiceDesk

Внутренняя система IT-заявок: сотрудник описывает проблему, администратор назначает исполнителя, исполнитель меняет статус и отвечает в комментариях. Dashboard и отчёты показывают данные из PostgreSQL с учётом роли пользователя.

Проект переработан на основе существующего приложения Next.js: сохранены App Router, подход с серверными API-маршрутами и идея сворачиваемой навигации. Интерфейс, предметная модель, хранение данных и авторизация заменены на ServiceDesk.

## Возможности

- Регистрация, вход, выход и профиль пользователя.
- Роли `EMPLOYEE`, `AGENT`, `ADMIN` с проверкой полномочий на сервере.
- Создание заявок, поиск, фильтры, сортировка, детали и комментарии.
- Назначение исполнителя администратором и изменение статуса назначенным исполнителем.
- Редактирование и удаление заявки в пределах бизнес-правил.
- Команда, управление ролями исполнителей и категории.
- Dashboard и отчёты по реальным доступным заявкам.
- Светлый адаптивный интерфейс, состояния загрузки, ошибок и пустых списков.

## Технологии

Next.js 16 / React 19, Tailwind CSS 4, PostgreSQL, Prisma ORM 7, Auth.js 5, Zod 4, Lucide React и Recharts. Точные версии зафиксированы в `package-lock.json`; устанавливайте зависимости командой `npm ci`.

Для запуска с настроенной общей базой нужны Node.js 24 и доступ в интернет. PostgreSQL уже размещена в Neon; устанавливать PostgreSQL или Docker на каждом компьютере не требуется. Приложение запускается локально в Node.js и обращается к общей базе.

## Установка

### Клон проекта с одной общей базой

Каждый компьютер запускает приложение на своём `localhost:3000`, а все экземпляры подключаются к одной PostgreSQL. Общая база уже настроена в проекте [ServiceDesk в Neon](https://console.neon.tech/app/projects/orange-waterfall-80178632): ветка `main`, PostgreSQL 17, регион Frankfurt. Существующие аккаунты и категории перенесены; текущий `.env` указывает на эту базу. Одинаковая `DATABASE_URL` на всех компьютерах даёт доступ к тем же аккаунтам, заявкам и комментариям.

На новом компьютере склонируйте GitHub-репозиторий и один раз перенесите приватный `.env` с этого компьютера в папку рядом с `package.json`. Передавайте файл отдельно от Git и сохраняйте уже настроенный `.env`. Затем выполните:

```powershell
npm.cmd ci
npm.cmd run db:setup
npm.cmd run dev
```

На macOS/Linux используйте `npm` вместо `npm.cmd`.

Проверьте точное имя перенесённого файла: **`.env` с точкой в начале**, рядом с `package.json`. Файлы `env`, `env.txt` и `.env.txt` приложение не читает. Для общей базы в `DATABASE_URL` должен быть адрес Neon; `localhost:5432` означает отдельную базу на текущем компьютере. После замены настроек полностью перезапустите `npm.cmd run dev`, чтобы обновилось подключение к базе. Сам `.env` не переносит аккаунты: они доступны через подключение к той же базе.

Git не переносит `.env`, локальные бинарники и данные из `.local/`, а также Docker volume. Если `.env` не копируется, получите подключение к той же базе в Neon и заполните собственный файл на основе `.env.example`. Создавайте шаблон только при отсутствии настроек:

```powershell
if (-not (Test-Path .env)) { Copy-Item .env.example .env }
```

На macOS/Linux используйте `[ -e .env ] || cp .env.example .env`. В `.env` задайте:

- `DATABASE_URL` — одну и ту же строку подключения к общей PostgreSQL на всех компьютерах, включая необходимые параметры TLS.
- `AUTH_URL="http://localhost:3000"` — адрес локального приложения; адрес сервера базы сюда не подставляется.
- `AUTH_SECRET` — случайный секрет сессий. Если значение уже задано, сохраните его. Для независимых запусков на разных компьютерах секреты могут отличаться; узлам одного сайта с общим адресом нужен одинаковый секрет.

Если `AUTH_SECRET` ещё пуст, создайте значение один раз и перенесите его в `.env`:

```powershell
node -e "console.log(require('node:crypto').randomBytes(32).toString('base64url'))"
```

Настройки и пароли остаются в `.env` и передаются участникам отдельно от Git. Скрипты запуска существующий `.env` не перезаписывают.

`db:setup` генерирует Prisma Client и применяет готовые миграции. Команда сохраняет существующие записи, не создаёт администратора и не сбрасывает пароли. Повторять bootstrap для каждого клона не нужно: входите существующим аккаунтом общей базы. Для следующих запусков достаточно `npm.cmd run dev`.

Откройте [http://localhost:3000](http://localhost:3000). Для новой пустой базы создайте первого администратора по разделу ниже. Если приложение размещается на общем веб-сервере, задайте его HTTPS-адрес в `AUTH_URL`.

### Альтернатива: отдельная PostgreSQL через Docker Compose

Этот вариант создаёт отдельную локальную базу вместо общей PostgreSQL в Neon. Для него настройте локальную `DATABASE_URL` и пароль PostgreSQL в `.env` в соответствии с `.env.example` и `compose.yaml`, затем запустите:

```powershell
docker compose up -d
```

Команда поднимает PostgreSQL, а приложение запускается отдельно. Данные базы находятся в Docker volume и сохраняются после перезапуска контейнера.

### Альтернатива: уже установленный PostgreSQL

Вместо Docker создайте пользователя и отдельную базу через pgAdmin или `psql`. В SQL-консоли администратора PostgreSQL:

```sql
CREATE ROLE servicedesk WITH LOGIN PASSWORD 'YOUR_DATABASE_PASSWORD';
CREATE DATABASE servicedesk OWNER servicedesk;
```

Обновите `DATABASE_URL` в `.env`. Если пароль содержит специальные символы, закодируйте их для URL. Убедитесь, что PostgreSQL доступен на указанном хосте и порту.

### Сохранённая локальная PostgreSQL на этом компьютере

До переноса в Neon использовалась PostgreSQL 17.11 из [официального архива EDB](https://www.enterprisedb.com/download-postgresql-binaries), база `servicedesk` на `127.0.0.1:5432` и отдельная роль `servicedesk` без прав суперпользователя. Исходный каталог `.local/postgres-data` сохранён как резервная копия. Текущий `.env` подключает приложение к Neon; новые изменения из облачной базы в эту локальную копию автоматически не переносятся.

Бинарники находятся в `.local/postgres`, данные — в `.local/postgres-data`, журнал — в `.local/postgres.log`. Эти каталоги исключены из Git. Данные сохраняются при остановке и перезагрузке; для сохранения заявок и аккаунтов не удаляйте каталог данных.

При текущей удалённой `DATABASE_URL` скрипт `predev` не запускает локальную PostgreSQL. Автоматический запуск используется только при переключении `.env` на сохранённую локальную базу. Для отдельного управления локальным кластером:

```powershell
npm.cmd run db:local:start
npm.cmd run db:local:status
npm.cmd run db:local:stop
```

`db:local:stop` отключает текущие соединения и откатывает незавершённые транзакции. Для отдельных локальных баз на других компьютерах используйте разделы выше. Для одних и тех же данных на всех устройствах подключите каждый клон к общему серверу PostgreSQL.

### Резервные копии и повторный перенос

Перенос существующих аккаунтов и категорий в общую базу уже выполнен. Для следующих резервных копий используйте `pg_dump`; локальные архивы храните в `.local/backups/`, который исключён из Git. Восстанавливайте копию через `pg_restore` в новую пустую базу, сохраняя таблицы приложения, последовательности и `_prisma_migrations`. Не используйте `migrate reset` и не запускайте демонстрационный seed для переноса.

На время окончательного переноса остановите запись в исходную базу. После восстановления выполните `db:setup`, проверьте аккаунты и заявки, затем укажите общую `DATABASE_URL` на всех компьютерах. Исходную локальную базу сохраните до проверки результата. Если целевая база уже содержит записи, сначала согласуйте перенос: обычное восстановление копии не объединяет две базы автоматически.

### Миграции и первый администратор

Только для новой базы задайте в `.env` переменные `BOOTSTRAP_ADMIN_NAME`, `BOOTSTRAP_ADMIN_EMAIL` и `BOOTSTRAP_ADMIN_PASSWORD` по `.env.example`. Для администратора через CLI допускается пароль от 11 символов; самостоятельная регистрация и смена пароля в профиле требуют не менее 12.

```powershell
npm.cmd run db:setup
npm.cmd run db:bootstrap
npm.cmd run dev
```

Bootstrap создаёт основные категории и администратора, не добавляя демонстрационные заявки. Повторный запуск сохраняет пароль существующего администратора. Команда не повышает права сотрудника, если указанный email уже принадлежит ему.

Перед запуском `dev` автоматически выполняется `prisma generate`, чтобы Prisma Client существовал и соответствовал текущей схеме. Локальная PostgreSQL запускается автоматически только при наличии локального кластера и соответствующей `DATABASE_URL`. Для ручной генерации используйте `npm.cmd run db:generate`.

Откройте [http://localhost:3000](http://localhost:3000). Войдите первым администратором. Самостоятельная регистрация создаёт только сотрудника; роль исполнителя назначает администратор на странице команды.

### Смена пароля администратора

Укажите email существующего администратора в `BOOTSTRAP_ADMIN_EMAIL` и новый пароль в `BOOTSTRAP_ADMIN_PASSWORD` внутри `.env`, затем выполните явную команду:

```powershell
npm.cmd run db:admin:password
```

Команда обновляет пароль только существующей учётной записи с ролью `ADMIN`, сохраняя заявки, комментарии и остальные данные. После смены в общей базе новый пароль действует для всех подключённых экземпляров. Изменение `.env` без этой команды пароль в базе не меняет; обычный запуск приложения также его не меняет. Пароли аккаунтов передавайте отдельно от репозитория.

### Демонстрационные данные

Seed запускается явно и предназначен для отдельной демонстрационной базы:

```powershell
$env:SEED_DEMO_PASSWORD = "YOUR_LONG_DEMO_PASSWORD"
npm run db:seed
```

Создаются пользователи `admin@servicedesk.demo`, `agent@servicedesk.demo`, `employee@servicedesk.demo` и связанные примеры заявок. Пароль берётся из `SEED_DEMO_PASSWORD` и должен содержать не менее 12 символов. Не размещайте пароль в репозитории. Повторный seed не меняет пароли существующих демонстрационных аккаунтов и не дублирует уже созданные примеры с тем же автором и названием. Данные seed записываются в PostgreSQL и участвуют в статистике как обычные записи. При обычном старте приложения seed не запускается.

## Права пользователей

| Действие | Сотрудник | Исполнитель | Администратор |
| --- | --- | --- | --- |
| Создать заявку | Да | Да | Да |
| Просмотреть заявку | Свои | Свои и назначенные | Все |
| Написать комментарий | В доступных заявках | В доступных заявках | Во всех |
| Редактировать / удалить | Своя новая неназначенная | Своя новая неназначенная | Любая |
| Изменить статус назначенной заявки | Нет | Если назначен | Да |
| Назначить исполнителя | Нет | Нет | Да |
| Управлять ролями команды | Нет | Нет | Да |
| Dashboard | Свои данные | Доступные данные | Все данные |
| Отчёты | Нет | Нет | Все данные |

Проверка выполняется в обработчиках API и при чтении данных на сервере. Скрытие кнопок помогает интерфейсу, но не даёт права на операцию. Роль сессии перепроверяется по текущей записи пользователя, поэтому изменение роли начинает действовать и для уже открытой сессии.

## API

JSON-маршруты находятся в `app/api`. Закрытые маршруты требуют cookie сессии Auth.js. Для запросов изменения данных в браузере используются тот же источник и `Content-Type: application/json`.

| Метод / адрес | Назначение |
| --- | --- |
| `POST /api/register` | Регистрация сотрудника: `name`, `email`, `password` |
| `/api/auth/*` | Вход, выход, CSRF и сессия Auth.js |
| `GET /api/tickets` | Доступные заявки и `total`, `page`, `pageSize` |
| `POST /api/tickets` | Создание: `title`, `description`, `categoryId`, `priority` |
| `GET /api/tickets/:id` | Детали и комментарии доступной заявки |
| `PATCH /api/tickets/:id` | Разрешённые поля заявки, назначение или статус по роли |
| `DELETE /api/tickets/:id` | Удаление заявки и связанных комментариев по правам |
| `POST /api/tickets/:id/comments` | Комментарий: `content`; автор определяется сессией |
| `GET /api/categories` | Категории для формы заявки |
| `POST /api/categories`, `PATCH /api/categories/:id`, `DELETE /api/categories/:id` | Управление категориями администратором; используемую категорию удалить нельзя |
| `GET /api/dashboard` | Счётчики, распределение, динамика и последние заявки |
| `GET /api/reports` | Полные отчёты для администратора |
| `GET /api/team` | Команда и нагрузка для администратора |
| `PATCH /api/team/:id` | Изменение `role` администратором |
| `GET /api/profile` | Текущий пользователь без хеша пароля |
| `PATCH /api/profile` | Имя; API также проверяет текущий пароль при смене email/пароля |

Параметры списка: `q`, `status`, `priority`, `sort=newest|oldest|priority|updated`, `mine=1`, `page`, `pageSize` (1–100). Статусы: `NEW`, `IN_PROGRESS`, `WAITING`, `RESOLVED`, `CLOSED`. Приоритеты: `LOW`, `MEDIUM`, `HIGH`, `URGENT`.

Создание возвращает `201`, чтение и изменение — `200`, удаление — `204`. Ошибки имеют JSON-поле `error`: неверные данные `400`, отсутствие входа `401`, запрет операции `403`, недоступная или отсутствующая заявка `404`, конфликт `409`, ограничение попыток входа/регистрации `429`. Недоступность базы возвращает понятную ошибку `503`, а подробности SQL и секреты не передаются клиенту.

## Структура

```text
app/             страницы App Router и серверные API-маршруты
components/      навигация, формы, таблицы, карточки и графики
lib/             Prisma-клиент, сессии, права, валидация и серверная логика
prisma/          schema.prisma, миграции, bootstrap и отдельный seed
tests/           unit- и интеграционные проверки
docs/            проверка, распределение работы, защита и GitHub
```

В PostgreSQL четыре связанные сущности: `User`, `Ticket`, `Category`, `Comment`. У заявки обязательны автор и категория, исполнитель может отсутствовать. Дополнительное `resolvedAt` хранит время решения для достоверной динамики отчётов. Комментарий связан с автором и заявкой. В базе хранится хеш пароля; исходный пароль не сохраняется и не возвращается API.

## Тестирование

`npm test` проверяет бизнес-правила доступа, серверные схемы Zod и хеширование пароля. Интеграционные проверки запускают собранный Next.js на свободном порту, регистрируют пользователей, получают настоящие Auth.js-сессии и обращаются к API.

Для интеграционных проверок создайте отдельную пустую базу, например командой SQL администратора PostgreSQL `CREATE DATABASE servicedesk_test OWNER servicedesk;`. Укажите её явно:

```powershell
$env:TEST_DATABASE_URL = "postgresql://servicedesk:YOUR_DATABASE_PASSWORD@localhost:5432/servicedesk_test?schema=public"
$previousDatabaseUrl = $env:DATABASE_URL
$env:DATABASE_URL = $env:TEST_DATABASE_URL
npm run db:migrate
$env:DATABASE_URL = $previousDatabaseUrl
npm run build
npm run test:integration
```

Миграция здесь применяется к тестовой базе. Интеграционные тесты не выполняют `reset`, не очищают таблицы целиком и удаляют только собственные записи. Без `TEST_DATABASE_URL` они останавливаются с понятным сообщением. Подключение обычного приложения автоматически не подставляется.

Проверяются вход, запрет повышения роли при регистрации, изоляция заявок, назначение исполнителя, изменение статуса, комментарии, серверная валидация и сохранение после перезапуска. Полный ручной сценарий, включая адаптивность, находится в [docs/CHECKS.md](docs/CHECKS.md). CI применяет миграции к PostgreSQL service и запускает unit-тесты, сборку и интеграционные проверки.

## Размещение

Разместите приложение на Node.js-хостинге с доступом к PostgreSQL. Настройте переменные окружения, затем выполните `npm ci`, `npm run db:generate`, `npm run db:migrate`, `npm run build`, `npm start`. На публичном сервере нужен HTTPS. Не запускайте демонстрационный seed при каждом деплое. Для данных и восстановления используйте резервные копии PostgreSQL.

В серверном терминале может появляться предупреждение `pg` о параллельных запросах: это [известная особенность Prisma PostgreSQL-адаптера](https://github.com/prisma/orm/issues/29407). На закреплённой версии `pg` 8 оно не прерывает запросы; операции и транзакции проверены интеграционными тестами. Предупреждения драйвера не подавляются.
